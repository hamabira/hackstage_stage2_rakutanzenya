# データ整合性ルール

不正な値や重複記録を防ぐための制約を、どこで・どう担保しているかをまとめる。DBスキーマは [supabase/migrations/](../supabase/migrations/) を参照。

## 役割分担

同じ検証を3層で重ねている。層ごとに目的が違うので、どれか1つだけにまとめることはしない。

| 層 | 担当箇所 | 目的 |
| --- | --- | --- |
| フォーム | [src/components/subjects/subjectFormValidation.ts](../src/components/subjects/subjectFormValidation.ts) | 入力中のフィードバック。送信前に画面上でエラー文を出す |
| 保存Action | Server Action(科目保存・記録保存) | 複数項目にまたがる検証。評価割合の合計100%など、1行だけでは判定できないもの |
| DB制約 | [supabase/migrations/0002_add_data_integrity_constraints.sql](../supabase/migrations/0002_add_data_integrity_constraints.sql) | 最終防衛線。SQL Editorや別クライアントからの直接操作も含めて不正値を拒否する |

フォームの検証はブラウザ側で動くため迂回できる。DB制約だけがどの経路からでも効くので、フォームを直したからといってDB制約を緩めない。

### 評価割合の合計100%をDB制約にしない理由

CHECK制約は1行しか見られない。評価割合の合計は `grade_items` の複数行にまたがるため、行単位のCHECKでは表現できない。トリガーやマテリアライズドビューで擬似的に実現することもできるが、途中状態(項目を1件ずつ追加していく操作)を全て弾いてしまうので採用していない。保存Actionでまとめて検証する。

## DB制約の一覧

`0002_add_data_integrity_constraints.sql` で追加しているもの。

| テーブル | 制約 | 内容 |
| --- | --- | --- |
| `subjects` | `total_class_count` NOT NULL + `_positive` | 総授業回数は必須かつ1以上 |
| `subjects` | `_attendance_required_rate_range` | 必要出席率は0〜100(百分率)。NULL可 |
| `subjects` | `_attendance_max_absences_range` | 最大欠席数は0以上かつ総授業回数以下。NULL可 |
| `subjects` | `_target_score_range` | 目標点数は0〜100。NULL可 |
| `grade_items` | `_weight_range` | 評価割合は0〜100 |
| `grade_items` | `_max_score_positive` | 満点は0より大きい。NULL可 |
| `test_records` | `_score_nonnegative` | 点数は0以上 |
| `attendance_records` | `_subject_id_class_date_key` | 同一科目・同一日付の出席記録は1件のみ |

必要出席率は **0〜100の百分率** で統一している。0〜1の比率として渡してはいけない(出席計算 [src/lib/calc/attendance.ts](../src/lib/calc/attendance.ts) も百分率前提)。

出席記録の一意制約により、保存処理では `onConflict: "subject_id,class_date"` を指定したUPSERTで「同じ日の記録を上書き」ができる。

## 既存Supabase環境への適用手順

`0001_init.sql` を適用済みの環境に後から制約を足す場合、既存データが制約に違反しているとALTER TABLE自体が失敗する。以下の順で進める。

### 1. 違反データの有無を確認する

SQL Editorで実行し、**すべて0件**であることを確認する。

```sql
-- subjects: 必須・範囲違反
select *
from subjects
where total_class_count is null
   or total_class_count <= 0
   or (attendance_required_rate is not null and attendance_required_rate not between 0 and 100)
   or (attendance_max_absences is not null and (attendance_max_absences < 0 or attendance_max_absences > total_class_count))
   or (target_score is not null and target_score not between 0 and 100);

-- grade_items: 評価割合・満点
select *
from grade_items
where weight not between 0 and 100
   or (max_score is not null and max_score <= 0);

-- test_records: 点数
select * from test_records where score < 0;

-- attendance_records: 同一科目・同一日付の重複
select subject_id, class_date, count(*)
from attendance_records
group by subject_id, class_date
having count(*) > 1;
```

### 2. 違反があれば手作業で直す

マイグレーションは既存データを自動修正しない。壊れ方によって正しい直し方が変わるため、意図しないデータ改変を避けている。典型的な対処は次の通り。

- **`total_class_count` がNULL/0以下**: シラバス等を確認して正しい回数を入れる。判断できない科目は削除する
- **必要出席率が100超**: 0〜1の比率(例: `0.8`)で入っている可能性が高い。100倍して百分率に直す
- **最大欠席数が総授業回数超**: 総授業回数の入力ミスか、最大欠席数の入力ミスかを確認して片方を直す
- **出席記録の重複**: 残す1件を決めて他を削除する。最新のみ残すなら以下

```sql
delete from attendance_records a
using attendance_records b
where a.subject_id = b.subject_id
  and a.class_date = b.class_date
  and (a.created_at, a.id) < (b.created_at, b.id);
```

`created_at` が同一のレコードが存在しても必ず1件だけ残るよう、`id` を第2キーにしている。

削除系のSQLは実行前に必ず `select` で対象を確認する。

### 3. マイグレーションを実行する

Supabase CLIで適用する。未適用のマイグレーションだけが実行されるため、適用済みのものを再実行してしまう心配はない。

```bash
supabase migration list   # Local と Remote の差分を確認
supabase db push          # 未適用のものを適用
```

各マイグレーションは1トランザクションで走るため、途中で失敗した場合は何も適用されない。エラーメッセージに出た制約名から違反箇所を特定し、手順1に戻る。

CLIを使わない場合は、対象SQLをSQL Editorに貼り付けて実行してもよい。ただしCLIの履歴テーブルに記録が残らないため、後からCLI運用へ切り替えると再実行しようとして失敗する。どちらで運用するかはチーム内で統一する。

### 4. 適用を確認する

`supabase migration list` で対象バージョンがLocalとRemoteの両方に並んでいれば適用済み。制約そのものを確認するには次のSQLを使う。

```sql
select conname, pg_get_constraintdef(oid)
from pg_constraint
where conrelid in ('subjects'::regclass, 'grade_items'::regclass, 'test_records'::regclass, 'attendance_records'::regclass)
  and contype in ('c', 'u')
order by conrelid::regclass::text, conname;
```

新規に立てた環境では `supabase db push` だけでよい(データが無いので手順1・2は不要)。

## 適用状況

`0002_add_data_integrity_constraints.sql` は共有Supabase環境へ適用済み(2026-08-08)。適用時点で制約違反の既存データは無かった。
